## 1. 项目定位

本项目目标是实现一个可以部署演示、可以持续迭代的通用 IoT 平台，而不是只完成几个 CRUD 接口。

当前采用“模块化单体”架构：公共能力拆成独立 Maven Starter，业务暂时集中在唯一可运行服务 `iot-server` 中。等 MQTT 接入、遥测处理等模块出现独立部署需求后，再考虑拆分服务。

项目借鉴 BladeX 的模块划分、自动配置、多租户、日志和注解授权思路，但不会直接复制完整微服务体系。当前优先完成最小可行平台，再持续增加企业级能力。

### 1.1 开发准则

后续开发统一遵守以下准则：

1. **以 `E:\share\iotwater\iot-be` 为主要对标项目。** 开发新模块或公共能力前，先查看对标项目中对应功能的模块职责、分层方式、命名习惯、数据模型和扩展点；能沿用的设计思路优先沿用。对标不等于原样复制，应结合本项目当前的 Spring Boot 3、模块化单体架构和实际业务范围做必要简化。
2. **开发阶段默认跳过自动化测试。** 日常编译、安装和阶段性构建统一使用 `-Dmaven.test.skip=true`，当前阶段以代码编译成功、应用实际启动和关键接口人工验证作为主要验收方式。已有测试失败暂不作为业务开发的阻塞条件；自动化测试体系在核心业务链路完成后集中补齐，除非某个高风险功能明确要求提前增加测试。
3. **基础设施只实现最小可行能力。** 日志、权限、多租户、Redis、监控、部署等基础设施以支撑当前业务闭环为完成标准，不提前追求完整企业级方案。已有基础设施允许在产品、设备、MQTT、遥测和告警开发过程中按实际需求持续迭代，不因非当前必需的完善项阻塞 IoT 核心业务开发。

当对标项目、通用最佳实践和当前阶段目标发生冲突时，优先保证当前业务闭环和可持续演进，并在本文档中记录主动简化项及后续补充时机。

#### 环节 8：动态物模型属性设计（已完成）

核心原则：数据库固定的是“属性定义的元数据结构”，不是温度、压力、流量等具体属性。平台用户可以针对每个产品动态新增任意数量的属性，每个属性作为一条定义记录保存。

对标 `iot-be` 后确认其采用：

- `iot_product_function_property` 保存属性名称、标识符、访问模式和产品关系。
- `iot_product_function` 保存数据类型以及最小值、最大值、单位、枚举、布尔文本、数组和结构体等规格。
- `iot_product_version` 在发布时保存整套物模型 JSON 快照。

当前项目按 MVP 原则简化为一张动态属性定义表，建议命名为 `iot_product_property`：

| 字段 | 类型建议 | 用途 |
|---|---|---|
| `id` | bigint | 属性定义主键 |
| `tenant_id` | varchar(12) | 租户隔离 |
| `product_id` | bigint | 所属产品 |
| `identifier` | varchar(64) | 设备报文中的属性标识符 |
| `property_name` | varchar(100) | 展示名称 |
| `access_mode` | varchar(2) | `r` 只读、`rw` 读写 |
| `data_type` | varchar(16) | int32、float、double、bool、text、enum、date 等 |
| `spec_json` | json | 当前数据类型对应的动态规格 |
| `required` | tinyint | 是否必需 |
| `description` | varchar(500) | 属性说明 |
| `sort_order` | int | 页面排序 |
| `status` | tinyint | 0-停用、1-启用 |
| `create_time` | datetime | 创建时间 |
| `update_time` | datetime | 更新时间 |
| `deleted` | tinyint | 逻辑删除 |

建议约束和索引：

- `UNIQUE (tenant_id, product_id, identifier)`：同一产品内属性标识符唯一。
- `INDEX (tenant_id, product_id, status)`：按产品读取有效物模型。
- 属性被逻辑删除后仍保留标识符占用，避免同一产品复用旧标识符表达不同含义，导致历史遥测语义混乱。

`spec_json` 根据 `data_type` 使用不同结构，例如：

```json
// double：温度
{"min":-40,"max":125,"step":0.1,"unit":"°C","unitName":"摄氏度"}

// bool：阀门状态
{"falseText":"关闭","trueText":"开启"}

// enum：工作模式
{"items":[{"value":0,"label":"自动"},{"value":1,"label":"手动"}]}

// text：故障描述
{"maxLength":500}
```

首版支持基础类型和枚举；`struct`、`array` 及嵌套参数在事件、服务模型出现实际需求后再扩展。JSON 规格使后续增加类型能力时不必修改属性表字段。

物模型归属于产品而不是单台设备：同一产品下的设备共享一套属性定义；如果新设备能力明显不同，应创建另一个产品并配置另一套属性。设备级属性覆盖不纳入当前 MVP。

后续发布设计：属性、事件和服务表保存可编辑草稿；增加 `iot_product_model_version` 后，将某个产品的完整物模型生成 JSON 快照并发布，设备接入和遥测校验只读取已发布版本。

该设计随后进入建表环节；用户在建表开始后授权 AI 直接完成，执行结果见环节 9。

##### 物模型业务概念校准

2026-09-23 对产品、设备和物模型关系完成确认：

- 物模型归属于产品，不直接归属于单台设备；同一产品下的所有设备实例共享同一套物模型。
- 创建水位计产品后，可由用户动态定义 `waterLevel`、`flowRate`、`alarm` 等属性及其数据类型、范围、单位和读写方式，不需要修改数据库表或 Java 实体。
- 属性不全部等同于“设备上传数据”：只读属性通常由设备上报，读写属性还可以由平台下发设置；主动发生的告警属于事件，重启、开阀等操作属于服务或命令。
- 平台允许动态选择和组合属性，但可用基础类型集合由平台预先支持；当前核对的 BladeX `FieldTypeEnum` 使用 `int32`、`float`、`double`、`text`、`date`、`bool`、`enum`、`struct`、`array`，而不是任意 Java 类型。
- 属性定义是数据协议和校验规则，不是设备实际上报的遥测值；设备实例和遥测存储属于后续阶段。
- 草稿物模型需要发布后才生成正式 JSON 快照，并供设备接入、缓存和时序数据结构使用；继续编辑草稿不应直接改变当前已发布版本。
- 如果两类设备能力不同，应分别建立产品；如果只是同型号的不同实物，应建立同一产品下的多个设备实例。

进一步确认三层业务关系：品类可作为某个行业/场景下的标准能力模板，产品通过 `category_id` 关联品类并拥有自己的物模型，设备实例通过 `product_key` 关联产品。以水文设备为品类时，水位计和流量计可以建立为两个产品；每个产品分别配置并发布物模型，再在产品下接入多台真实设备。

设备上报值使用物模型 `identifier` 与属性定义对应。物模型负责描述允许的数据结构、类型、范围、单位和权限；遥测记录保存设备标识、采集时间和实际属性值。BladeX 发布产品物模型后，会依据属性列表动态创建或调整 TDengine 产品超级表字段，因此不同产品可以拥有不同遥测字段，同一产品的设备共享相同字段结构。

物模型配置完成只代表平台知道设备数据的字段、类型和含义，不能直接执行规则。规则动作的完整前置链路应为：已发布物模型 -> 设备档案与唯一身份 -> HTTP/MQTT 数据接入 -> 厂商字段映射和物模型校验 -> 保存设备最新值及历史数据 -> 规则引擎读取本次值、上次值或时间窗口 -> 条件命中后执行动作。以水位为例，可以配置 `waterLevel > 5.5` 后生成高水位告警、发送通知、调用设备服务、转发数据或发起 Agent 诊断；规则负责确定性检测，Agent 根据当前值、历史趋势、相关事件和知识库解释原因并给出处置建议。

既有 Agent 接入采用适配而非整库复制：在 IoT 平台提供内部诊断上下文接口，或为 Agent 增加 `get_device_profile`、`get_current_properties`、`query_telemetry_history`、`query_recent_events`、`query_active_alarms` 和 `search_knowledge` 等受控工具；新增结构化诊断请求与结果，至少记录设备、触发告警、诊断结论、证据、建议、置信或不确定性以及调用时间。两个工程的 Spring Boot 版本不同，因此第一阶段优先保持独立服务并通过内部 HTTP 调用，避免直接复制代码和依赖造成版本冲突；数据链路稳定后再决定是否合并模块。下一开发阶段仍从物模型发布快照开始，随后完成设备与数据接入，再实现最小规则引擎和 Agent 适配。
