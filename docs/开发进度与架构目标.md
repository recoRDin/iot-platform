## 1. 项目定位

本项目不是只完成几个 CRUD 接口，而是逐步实现一个可以部署演示、能够写入秋招简历的通用物联网平台底座。

平台面向暂时没有真实硬件的开发场景，先使用设备模拟器通过 MQTT 上报数据，后续再扩展边缘网关和真实设备接入。

目标能力包括：

- 产品管理与物模型。
- 设备注册、身份鉴权和生命周期管理。
- MQTT 设备消息接入、解析和路由。
- 设备实时状态与历史遥测数据。
- 告警规则、告警记录和通知流程。
- 多租户、用户、角色和数据权限。
- 缓存、日志、链路标识、异常处理等平台基础设施。
- 设备模拟器与可部署的演示环境。
- 最后增加 AI 运维助手，首个方向是设备故障诊断。

## 2. 架构目标

### 2.1 当前阶段采用“模块化单体”

当前只保留一个可运行服务 `iot-server`。公共能力拆成独立 Maven JAR 模块，但整个业务先作为一个 Spring Boot 应用部署。

这样设计的原因：

- 学习阶段只有一个人开发，单体更容易理解、调试和部署。
- 通过 Maven 模块和 Java 包边界保持职责清晰，不把所有代码堆进启动模块。
- 产品、设备、告警等业务成熟后，可以根据吞吐量和部署需要拆成独立服务。
- 企业级不等于启动类越多；当前更重要的是边界、可靠性、安全性和可部署性。

### 2.2 目标逻辑架构

```text
管理端 / 开放 API
        |
        v
iot-server（当前唯一启动入口，管理面与业务编排）
        |
        +-- 用户、租户、角色、权限
        +-- 产品、物模型、设备档案
        +-- 告警规则与告警记录
        +-- 操作日志与平台配置

设备模拟器 / 边缘网关
        |
        v
MQTT Broker（计划使用 EMQX，属于外部消息基础设施）
        |
        v
MQTT 接入与消息处理模块（尚未创建）
        |
        +-- 设备鉴权与上下线状态
        +-- 属性上报、事件上报、服务调用
        +-- 实时状态缓存 Redis
        +-- 元数据 MySQL
        +-- 历史遥测存储（技术方案尚待确定）
        +-- 规则计算与告警
        |
        v
AI 运维助手（最后阶段，读取设备、遥测、告警和日志进行故障诊断）
```

## 3. BladeX 对齐原则

项目借鉴 BladeX 的工程组织和组件职责，但不照搬其全部微服务复杂度。

已经采用的思路：

- 根工程、`iot-core`、`iot-service` 使用 Maven 聚合工程。
- 公共组件按职责拆成可复用 JAR，而不是让业务模块依赖一个笼统的“大 core”。
- Starter 通过 Spring Boot 自动配置接入。
- 使用 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 显式登记自动配置类。
- 使用 `@ConditionalOnMissingBean` 提供可被业务系统替换的默认 Bean。
- 日志采用“注解 + AOP + 事件发布 + 监听器”的解耦思路。
- 公共组件不直接承载产品、设备、告警等业务逻辑。

与 BladeX 的主要差异：

- 使用 Spring Boot 3.2.10、Java 17 和 Jakarta Servlet API。
- 当前采用模块化单体，而不是一开始就搭建完整微服务集群。
- 只引入物联网平台真正需要的组件。
- 日志、权限、多租户和数据接入将按学习节奏逐步实现。

## 4. 当前 Maven 模块结构

```text
iot-learning                         根聚合工程，packaging=pom
├── iot-core                         公共组件聚合工程，packaging=pom
│   ├── iot-core-tool                基础返回对象与结果码，jar
│   ├── iot-core-boot                Web/Jackson/CORS 自动配置，jar
│   ├── iot-starter-log              异常、链路和 API 日志基础，jar
│   ├── iot-starter-mybatis          MyBatis-Plus 数据访问基础，jar
│   └── iot-starter-redis            Redis 缓存基础，jar
└── iot-service                      可运行服务聚合工程，packaging=pom
    └── iot-server                   当前唯一 Spring Boot 服务，jar
```

三个 `packaging=pom` 的聚合模块负责组织子模块和继承关系，本身不承载运行代码。真正打成 JAR 的是各个 starter、tool 和 `iot-server`。

`iot-server` 按需依赖具体 core 组件。`iot-core` 只是聚合目录，不应被整体依赖。

### 5.7 日志与链路基础

位置：`iot-core/iot-starter-log`

已完成：

- 开发环境 Logback 控制台日志配置。
- 生产环境控制台、INFO 滚动文件和 ERROR 滚动文件配置。
- 日志格式包含 `traceId`。
- `TraceIdFilter`：
  - 接收合法的上游 `X-Trace-Id`，否则生成 UUID。
  - 写入 SLF4J MDC。
  - 将 traceId 写入响应头。
  - 在请求结束后清理 MDC，避免线程复用造成串号。
- `@ApiLog` 方法注解。
- `LogAbstract` 和 `LogApi` 日志模型。
- `ApiLogAspect`：拦截带 `@ApiLog` 的成功调用，统计耗时并创建 `LogApi`。
- `ApiLogPublisher` 和 `ApiLogEvent`：使用 Spring 应用事件解耦日志采集与消费。
- 日志相关 Bean 已由 `IotLogAutoConfiguration` 自动注册。

当前 API 操作日志链路为：

```text
请求
  -> TraceIdFilter 写入 MDC
  -> Controller 中带 @ApiLog 的方法
  -> ApiLogAspect 执行原方法并计算耗时
  -> ApiLogPublisher 发布 ApiLogEvent
  -> 监听器（尚未创建）
  -> 后续异步保存数据库
```

当前注意事项：

- `ApiLogAspect` 只发布成功执行的方法日志；异常继续向外抛给 `RestExceptionTranslator`，避免重复记录。
- `ApiLogAspect` 中还残留未使用的 `Logger` 导入和字段，可以在下一次整理时删除。
- `requestUri`、HTTP method、客户端 IP、User-Agent、请求参数、租户和操作人等字段尚未填充。
- `ApiLogEvent` 当前使用 Spring 默认同步事件机制。
- `ApiLogListener` 尚未创建，因此事件发布后目前没有业务消费者。
- API 日志数据库表、Mapper、Service 和持久化流程尚未建立。
- 错误日志 `LogError` 和普通日志 `LogUsual` 尚未开始。

## 9. 企业级验收标准

最终达到“可写入简历、可部署试用”，至少需要满足：

- 可以用 Docker Compose 或明确脚本启动依赖和平台。

- 用户、角色、租户之间存在真实的数据隔离。
- 错误返回统一，日志可通过 traceId 关联一次请求。
- 密码、数据库口令和设备密钥不能写死在仓库中。
- 对非法设备、错误消息、重复数据和依赖故障有明确处理。
- 有最小但有效的自动化测试、部署文档和演示数据。
